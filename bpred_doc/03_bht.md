## 0. Краткая теория (по книге Martínez Aceves)

**Динамическое** предсказание направления учится на истории исполнения. Базовая
структура — **BHT (Branch History Table)**: массив **насыщающихся счётчиков**,
индексируемый срезом PC. Классический счётчик — **2-битный**, 4 состояния:
```
00 strongly-NT   01 weakly-NT  |  10 weakly-T   11 strongly-T
 └──── предсказ. НЕ взят ──────┘   └──── предсказ. взят ──────┘
        (старший бит счётчика = предсказанное направление)
```
После разрешения перехода счётчик двигается к факту (взят → +1 до насыщения; не
взят → −1). **Смысл двух бит (гистерезис):** одна аномалия (например, последняя
итерация цикла — «не взят») **не переворачивает** предсказание; нужно две подряд.
Это заметно точнее 1-битного счётчика на реальном коде.

Зачем поверх BTFN: статика угадывает «в среднем», а BHT ловит **индивидуальное
поведение** каждой ветки (например, forward-ветку, которая на деле почти всегда
взята — BTFN бы ошибался каждый раз). В нашей связке (см. [BTFN](02_btfn.md)) необученная
запись отдаёт `valid=0`, и предсказатель падает обратно на BTFN.

---

## 1. Зачем он нужен (смысл)

BTFN ошибается на ветках, чьё поведение противоречит правилу знака (forward-taken,
backward-not-taken, дата-зависимые ветки). BHT **запоминает** фактическое
направление каждой ветки в маленьком счётчике и предсказывает по нему. По нашим
замерам динамический BHT — **крупнейший единичный вклад на coremark** (там ветки
разнообразнее, чем циклы dhrystone).

Кроме главной (поздней) роли, BHT даёт **второй порт чтения** для раннего
fetch-side гейта BTB (§01 §4.2): он подтверждает направление *до* steer'а, чтобы не
рулить переходами, которые окажутся не-взятыми.

---

## 2. Принцип работы

`SCR1_BP_BHT_SIZE = 1024` записей, каждая = `{valid, sat[1:0]}`. Индекс —
`pc[10:1]` (`SCR1_BP_BHT_IDX_W = 10`). Чтение комбинационное (два независимых
порта). Обновление — из EXU на каждом разрешённом условном переходе.

### 2.1 Индекс `pc[10:1]` — и почему не `pc[10:2]` как у BTB

Возьмём условный переход по `PC = 0x1246`:
```
index = pc[10:1]
0x1246 = …0001_0010_0100_0110(2)
         bit:      10        1
              └── pc[10:1] ──┘   ← 10 бит → 1024 записи
```
`0x1246` → `pc[10:1] = 0b01_0010_0011 = 0x123 = 291`. Соседняя полу-команда по
`0x1244` → `pc[10:1] = 0x122 = 290` — **другая запись**.

**Ключевое отличие от BTB:** BHT берёт бит `pc[1]`, а BTB — нет (`pc[9:2]`). Почему?
BTB слово-гранулярный (одна запись на fetch-слово из двух полу-команд), а BHT
должен различать **две RVC-ветки в одном слове** — у них разное направление, им
нужны разные счётчики. Отсюда `pc[1]` в индексе BHT. И именно поэтому BTB **хранит**
`bht_index` в своей записи: на фетче `pc[1]` неизвестен, а fetch-side гейт обязан
прочитать счётчик *настоящей* ветки (см. §4.2 и [BTB](01_btb.md) §5).

## 3. Разбор кода модуля (`scr1_pipe_bht.sv`)

**Хранилище** (стр. 52–53) — упакованные векторы (сброс одним оператором, без
for-цикла, который отвергают некоторые тулы):
```systemverilog
logic [SCR1_BHT_SIZE-1:0]      valid_q;   // обучена ли запись
logic [SCR1_BHT_SIZE-1:0][1:0] sat_q;     // 2-битный счётчик, MSB = направление
```

**Два порта чтения** (стр. 57–63):
```systemverilog
assign bht_valid_o  = valid_q[bht_rindex_i];       // главный (поздний): индекс = ifu_head_pc[10:1]
assign bht_taken_o  = sat_q[bht_rindex_i][1];
assign bht_valid2_o = valid_q[bht_rindex2_i];      // fetch-side: индекс из BTB
assign bht_taken2_o = sat_q[bht_rindex2_i][1];
```
Второй порт — целиком ради раннего гейта BTB; читается комбинаторно.

**Обновление** (стр. 67–83):
```systemverilog
if (~rst_n) begin valid_q<='0; sat_q<='0; end
else if (bht_upd_vd_i) begin
    valid_q[idx] <= 1'b1;
    if (~valid_q[idx])            sat_q[idx] <= taken ? 2'b10 : 2'b01; // 1-й раз: сразу к weak
    else if (taken)  if (sat!=2'b11) sat_q[idx] <= sat + 1;           // насыщение вверх
    else             if (sat!=2'b00) sat_q[idx] <= sat - 1;           // насыщение вниз
end
```
**«Тёплый старт» (стр. 73–76):** при первом наблюдении счётчик не стартует с
`00`/`11`, а **прыгает к слабому состоянию, совпадающему с фактом** (`10` если
взят, `01` если нет). Так следующее же предсказание уже трекает ветку — учимся за
один шаг, а не за два mispredict'а.

## 4. Куда он вставлен в ядро

### 4.1 Инстанс и главный порт (`scr1_pipe_ifu.sv:886–907`)

```systemverilog
scr1_pipe_bht #(...) i_bht (
    .bht_rindex_i    (ifu_head_pc[SCR1_BP_BHT_IDX_W:1]), // поздний: индекс головы очереди
    .bht_valid_o(bht_valid), .bht_taken_o(bht_taken),    // → в BTFN (bp_bht_valid/taken_i)
    .bht_rindex2_i   (btb_bht_index_fetch),              // fetch-side: индекс из BTB
    .bht_valid2_o(btb_bht_valid_fetch), .bht_taken2_o(btb_bht_taken_fetch),
    .bht_upd_vd_i    (exu2ifu_bp_upd_vd_i),              // обучение из EXU
    .bht_upd_index_i (exu2ifu_bp_upd_index_i),
    .bht_upd_taken_i (exu2ifu_bp_upd_taken_i) );
```

### 4.2 Fetch-side гейт (связь с BTB)

Второй порт читается по `btb_bht_index_fetch` (сохранённый в BTB индекс ветки) и
даёт `btb_bht_valid_fetch/taken_fetch`, из которых IFU строит
`btb_dir_ok = ~is_cond | (bht_valid & bht_taken)` (`ifu:959`) — условие раннего
steer'а. Так BTB рулит условной веткой, **только если её счётчик обучен-и-взят**.

### 4.3 Обучение и «круговорот индекса» (`scr1_pipe_exu.sv:880–882`)

```systemverilog
exu2ifu_bp_upd_vd_o    = exu_queue_vd & exu_queue.branch_req & exu_rdy; // один импульс на retire
exu2ifu_bp_upd_index_o = exu_bp_index;    // ← индекс, ПОСЧИТАННЫЙ НА ФЕТЧЕ
exu2ifu_bp_upd_taken_o = branch_taken;    // фактический исход
```
Индекс не пересчитывается при retire: он вычислен на фетче
(`ifu2exu_bp_index_o = ifu_head_pc[10:1]`, `ifu:1135`), едет с командой в EXU
(`ifu2exu_bp_index_i` → защёлкивается в `bp_index_ff`, `exu:416`) и возвращается на
обучение. Это гарантирует, что обучается **ровно та запись**, из которой было
сделано предсказание (важно при RVC, где `pc[1]` неоднозначен по слову).
`exu_rdy` даёт один импульс — иначе застопорившийся переход инкрементил бы счётчик
каждый такт.

## 5. Почему так, и как можно было иначе

| Решение | Почему так | Альтернатива и её цена |
|---|---|---|
| **2-битный насыщающийся** | гистерезис: одна аномалия (хвост цикла) не переворачивает предсказание; классический хороший ROI | *1-битный*: дешевле, но на чередующихся/хвостах циклов заметно хуже; *gshare/глобальная история*: точнее на коррелированных ветках, но сложнее (см. книгу) — избыточно для MCU-ядра |
| **`valid` + тёплый старт к weak** | учится за 1 шаг; необученные записи честно отдают `valid=0` → fallback на BTFN | без `valid`, инициализация всех в weak-taken: нельзя откатиться на BTFN, forward-ветки стартуют неверно |
| **Индекс `pc[10:1]`** | различает две RVC-ветки в одном слове (у них разное направление) | `pc[10:2]` (как BTB): две RVC-ветки слова слились бы в одну запись → взаимная порча |
| **Регистры, не RAM** | маленькая таблица, простой синхронный сброс `valid` | block-RAM: сброс valid требует отдельной init-логики; выигрыш по площади мал на 1024×3 бит |
| **Второй порт чтения (fetch-side)** | нужен раннему гейту BTB до steer'а | без него — слепой steer → misfetch-флаши (так было в первой версии) |
| **Круговорот индекса fetch→EXU→train** | обучается ровно предсказавшая запись; не надо пересчитывать `pc[1]` на retire | пересчитать индекс из `pc_curr_ff[10:1]` в EXU: обычно совпадёт, но лишний риск рассинхрона при RVC |
| **1024 записи** | достаточно, чтобы рабочее множество веток coremark мало конфликтовало | меньше — больше aliasing'а (две ветки делят счётчик → взаимные ошибки); больше — площадь без выигрыша |

## Резюме одной строкой

BHT — таблица 1024×(2-бит счётчик + valid), индексируемая `pc[10:1]`, обучаемая EXU
на retire по индексу, посчитанному ещё на фетче. Старший бит счётчика — направление;
`valid` даёт откат на [BTFN](02_btfn.md) у необученных записей; второй порт чтения питает
ранний гейт [BTB](01_btb.md). Гистерезис двух бит и тёплый старт делают её крупнейшим
единичным вкладом на coremark.
