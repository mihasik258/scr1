# Часть 4 — RAS (Return Address Stack, предсказание возвратов)

Файл модуля: [`scr1_pipe_ras.sv`](../src/core/pipeline/scr1_pipe_ras.sv)
Точки вставки: `scr1_pipe_ifu.sv` (детект call/return + инстанс + арбитрация).
Происхождение: адаптация `ras.sv` из OpenHW CVA6 (Solderpad HW License v2.0).

---

## 0. Краткая теория (по книге Martínez Aceves)

Возврат из функции (`ret` = `jalr x0, 0(x1)`) — это **косвенный** переход: цель не
закодирована в команде (она в регистре `ra`) и **меняется от вызова к вызову**.
Ни BTFN (§02, цель = PC+imm), ни BTB (§01, один кэшированный target на запись) не
справятся: одна и та же функция, вызванная из разных мест, должна вернуться в
разные точки — один target на PC возврата всегда мажет.

**RAS** решает это структурно: маленький **стек** адресов возврата. `call`
(`jal/jalr` с записью в link-регистр) кладёт на вершину адрес *следующей* за собой
команды; `return` снимает вершину — это и есть предсказанная цель. Стек **зеркалит
вложенность call/return**, поэтому предсказывает правильную точку возврата для
каждого динамического вызова. На реальном коде RAS почти идеально предсказывает
возвраты при разумной глубине.

---

## 1. Зачем он нужен (смысл)

Без RAS каждый `ret` — mispredict (косвенная цель неизвестна на фетче/декоде).
Функции вызываются часто, и промах возврата стоит флаша конвейера. RAS убирает эти
промахи, отслеживая адреса возврата по мере вызовов.

Корректность здесь тоже держится на EXU: RAS — только подсказка, а неверная вершина
приведёт лишь к mispredict, не к ошибке. Поэтому — и это наше сознательное отличие
от оригинала CVA6 — **стек никогда не флашится** (см. §5).

---

## 2. Принцип работы

Сдвиговый стек глубины `SCR1_RAS_DEPTH = 4` из записей `{valid, ra}`. Вершина
`stack_q[0]` — предсказание. `push` вдвигает новый адрес на вершину и сдвигает
остальные вниз; `pop` выдвигает вершину и сдвигает вверх. Вершина валидна ⟺
`stack_q[0].valid`.

---

## 3. Разбор кода модуля (`scr1_pipe_ras.sv`)

**Запись и хранилище** (стр. 33–39): структура `{valid, ra}`, массив глубины 4,
комбинационное «следующее состояние» `stack_d` + регистр `stack_q`.

**Выход = вершина** (стр. 42–43): `ras_valid_o = stack_q[0].valid`,
`ras_data_o = stack_q[0].ra`.

**Логика стека** (стр. 45–71):
```systemverilog
stack_d = stack_q;                         // по умолчанию держим
if (ras_push_i) begin                      // call: новый ra на вершину, сдвиг вниз
    stack_d[0] = {1'b1, ras_data_i};
    stack_d[DEPTH-1:1] = stack_q[DEPTH-2:0];
end
if (ras_pop_i) begin                       // return: сдвиг вверх, низ обнуляем
    stack_d[DEPTH-2:0] = stack_q[DEPTH-1:1];
    stack_d[DEPTH-1] = '0;
end
if (ras_pop_i && ras_push_i)               // одновременный pop+push: просто заменить вершину
    stack_d = stack_q; stack_d[0] = {1'b1, ras_data_i};
if (ras_flush_i) stack_d = '0;             // высший приоритет (у нас не используется)
```
Приоритет: `flush` > `pop&&push` (co-routine) > одиночные push/pop. Одновременный
push+pop — это `call`, стоящий на месте `return` (хвостовые/сопрограммы): вершина
просто заменяется, глубина не меняется.

## 4. Куда он вставлен в ядро (`scr1_pipe_ifu.sv:1031–1090`)

### 4.1 Детект call/return по ABI (стр. 1047–1064)

RISC-V ABI: link-регистры — `x1` (`ra`) и `x5` (`t0`). Детект по полям команды на
выходе очереди, покрывает RVI и RVC:
```systemverilog
ras_rd_link  = (rd  == x1) | (rd  == x5);   // пишет в link-регистр?
ras_rs1_link = (rs1 == x1) | (rs1 == x5);   // читает из link-регистра?
rvi_jal/rvi_jalr = opcode 1101111 / 1100111;
rvc_jr/rvc_jalr  = C2, funct3=100, rs2==0, bit12=0/1;   c.jal = C1, funct3=001;
ras_is_call   = (jal|jalr с rd=link) | c.jalr | c.jal;
ras_is_return = (jalr с rs1=link и rd≠link) | (c.jr с rs1=link);
```
Это ровно архитектурная эвристика call/return из спецификации (переход через
link-регистр = call/return).

### 4.2 Push/pop и адрес возврата (стр. 1066–1082)

```systemverilog
ras_link = ifu_head_pc + (q_head_is_rvc ? 2 : 4);   // адрес СЛЕДУЮЩЕЙ команды = точка возврата
ras_push = ras_is_call   & bp_instr_consumed & ~exu2ifu_pc_new_req_i;
ras_pop  = ras_is_return & ras_top_valid     & bp_instr_consumed & ~exu2ifu_pc_new_req_i;
```
`push/pop` происходят только когда команда реально принята IDU
(`bp_instr_consumed`) и нет архитектурного редиректа EXU.

### 4.3 `flush` подвязан к нулю (стр. 1076)

```systemverilog
.ras_flush_i (1'b0),  // никогда не флашим
```
**Осознанное отличие от CVA6.** Комментарий в коде: EXU всегда проверяет цель →
корректность держится; флаш — лишь перф-эвристика, а очистка стека на *каждом*
редиректе разрушает его содержимое. На 3-ступенчатом ядре чистить стек дороже, чем
изредка иметь устаревшую вершину.

### 4.4 Арбитраж (стр. 1085–1090)

```systemverilog
ras_predict_vd = ras_is_return & ras_top_valid;
bp_any_taken   = bp_predict_taken | ras_predict_vd;             // возврат тоже «взят»
bp_any_target  = ras_predict_vd ? ras_top : bp_predict_pc;      // возврат ПЕРЕОПРЕДЕЛЯЕТ цель BTFN
```
Предсказание возврата имеет приоритет над BTFN-целью (см. [интеграцию](05_integration.md)).

## 5. Почему так, и как можно было иначе

| Решение | Почему так | Альтернатива и её цена |
|---|---|---|
| **Стек (а не BTB) для возвратов** | возврат косвенный и зависит от места вызова; стек зеркалит вложенность → верная цель на каждый динамический вызов | один target/PC в BTB: мажет, когда функцию зовут из разных мест |
| **Глубина 4** | покрывает типичную вложенность вызовов этих ворклоадов; дёшево по FF | глубже: убывающая отдача здесь; мельче: переполнение на глубокой рекурсии → промахи |
| **Никогда не флашить (`flush=0`)** | EXU ловит неверный возврат; флаш на каждом редиректе опустошает стек и убивает hit-rate | флаш на mispredict (дефолт CVA6): «правильнее» спекулятивно, но на нашем ядре хуже по попаданиям |
| **Детект по link-регистрам x1/x5** | это архитектурная конвенция call/return в RISC-V ABI | эвристики по одному opcode: не отличат call от обычного jalr, ложные push/pop |
| **push=адрес следующей команды** | это и есть точка возврата (`ra`), которую положил бы сам `call` | хранить что-то другое: не совпадёт с реальным `ra` |
| **Обработка одновременного push+pop** | хвостовые вызовы/сопрограммы не должны менять глубину | игнорировать: рассинхрон глубины стека |

---

## Резюме одной строкой

RAS — сдвиговый стек глубины 4 из `{valid, ra}`: `call` (переход через link-регистр
x1/x5) кладёт адрес следующей команды, `return` снимает вершину как предсказанную
цель. Он единственный корректно предсказывает косвенные возвраты (BTB/BTFN тут
бессильны), его вершина переопределяет цель BTFN в общем арбитраже
([интеграцию](05_integration.md)), и он сознательно **не флашится** — корректность гарантирует
EXU, а флаш только испортил бы hit-rate.
